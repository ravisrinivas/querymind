# Data Dictionary — QueryMind demo database (e-commerce, SQLite)

Synthetic data generated by `backend/data/seed_db.py` (seed 42). Orders span **2023-01-01 → 2025-12-31**; the demo's fixed "today" is **2025-12-31**.

| Table | Rows | Purpose |
|---|---|---|
| `categories` | 12 | Product departments |
| `suppliers` | 40 | Vendors (country, lead time) |
| `products` | 1,000 | Catalogue; FK → categories, suppliers |
| `customers` | 1,200 | Accounts; `email` is **sensitive** |
| `orders` | 5,000 | Order headers; FK → customers |
| `order_items` | 10,544 | Order lines — **many-to-many** between orders and products |
| `payments` | 4,970 | One per non-pending order |
| `shipments` | 4,555 | One per shipped/completed/returned order |
| `reviews` | 3,000 | 1–5 star product reviews |

## Relationships
```
categories 1─* products *─1 suppliers
customers  1─* orders   1─* order_items *─1 products     (orders ↔ products is many-to-many)
orders     1─0..1 payments        orders 1─0..1 shipments
customers  1─* reviews *─1 products
```

## Columns
- **categories** — `category_id` PK · `name` · `parent_category_id` (unused, NULL)
- **suppliers** — `supplier_id` PK · `name` · `country` (supplier's country) · `lead_time_days`
- **products** — `product_id` PK · `name` · `category_id` FK · `supplier_id` FK · `unit_price` (current list price) · `cost_price` · `created_at` DATE · `is_active` (1/0)
- **customers** — `customer_id` PK · `first_name` · `last_name` · `email` *(sensitive)* · `country` · `city` · `segment` (Consumer / Corporate / Small Business) · `signup_date` DATE
- **orders** — `order_id` PK · `customer_id` FK · `order_date` DATE · `status` (pending, shipped, completed, cancelled, returned) · `shipping_cost` · `tax_amount` · `total_amount` (= items + shipping + tax)
- **order_items** — `order_item_id` PK · `order_id` FK · `product_id` FK · `quantity` · `unit_price` (price at sale time) · `discount_pct` (0–0.3) · `line_total` (= quantity × unit_price × (1 − discount_pct))
- **payments** — `payment_id` PK · `order_id` FK · `payment_date` DATE · `method` (credit_card, paypal, bank_transfer, gift_card) · `amount` · `status` (captured, refunded, failed)
- **shipments** — `shipment_id` PK · `order_id` FK · `carrier` · `shipped_date` DATE · `delivered_date` DATE (NULL while in transit) · `status` (in_transit, delivered, returned)
- **reviews** — `review_id` PK · `product_id` FK · `customer_id` FK · `rating` 1–5 · `review_date` DATE · `comment` (nullable)

## Assignment requirements → where they are met
| Requirement | How |
|---|---|
| ≥ 6 tables with FKs and many-to-many | 9 tables; `order_items` bridges orders ↔ products |
| ≥ 3 aggregate patterns | SUM, COUNT, AVG with GROUP BY across 15+ library examples |
| ≥ 2 date fields needing temporal arithmetic | `order_date`, `signup_date`, `shipped_date`, `delivered_date`, `review_date` (delivery-time and day-difference queries) |
| Schema ambiguity | **"revenue"** → `orders.total_amount` · `order_items.line_total` · `payments.amount`; also `country` (customers vs suppliers), `price`, `status` |
| ≥ 1,000 rows per primary table | products 1,000 · customers 1,200 · orders 5,000 · order_items 10,544 · payments 4,970 · shipments 4,555 · reviews 3,000 |

## Revenue convention (editable in Model config → Business rules)
Cancelled orders are excluded. Order/customer/country/time-level revenue = `SUM(orders.total_amount)`. Product/category-level revenue = `SUM(order_items.line_total)`. `payments.amount` is used only for money-collected or refund questions. The Schema Linker resolves the term by FK-graph proximity to the other entities in the question (e.g. "revenue by category" → `order_items.line_total`), falls back to the `*`-marked default, and can ask the user to choose.
